How each app implements it
Android

Search runs in SearchActivity, which hosts SearchFragment. That fragment switches between a recent-searches panel (RecentSearchesFragment) and a Compose results panel (SearchResultsFragment and SearchResultsScreen). Results come from a Paging 3 flow, debounced by 200 ms, that fetches a prefix search plus a full-text fallback from the MediaWiki API. The prefix page can also be prepended with one match each from open tabs, history and reading lists. Recent searches are stored in Room. I did not inspect the analytics wiring beyond the Test Kitchen events, the voice-search launcher, or the main-screen search bar.

iOS

iOS search is a UISearchController in SearchViewController. Its results controller, SearchResultsViewController, switches between a recent-searches list and a SwiftUI results list. Typing triggers a 100 ms delayed async search. Each search is a prefix search (generator=prefixsearch, limit 24), followed by a full-text search when the prefix search returns fewer than 12 results. Recent searches are stored in a plist-backed MWKRecentSearchList, saved only when a result is tapped. Entry points: the search tab, the article toolbar, widgets via a wikipedia://search deep link, and NSUserActivity. I did not read the language bar controller, the results view model's highlighting and image loading, or the recent-search entry and plist storage details.
